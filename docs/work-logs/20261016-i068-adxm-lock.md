# 작업 로그: CRI ADXM 잠금의 상호 배제 (issue #68)

설계: [20261016-i068](../design/20261016-i068-adxm-lock.md) · 작업 지시: [20261016-i068](../work-orders/20261016-i068-adxm-lock.md)

## 한 일

1. 사용자 정지 보고(v0.0.29)를 디스어셈블과 대조했다.
   * present 스레드는 `0x001437B0`의 `GetThreadPriority == 15` 루프에 있었다.
   * 그 루프가 기대하는 잠금은 CRI SVM/ADXM 잠금이다. 전역 횟수와 저장 우선순위 하나로 동작하고, 상호 배제는 단일 코어 우선순위에만 기댄다([cri-middleware](../analysis/cri-middleware.md)).
2. 런타임에 게스트 잠금(`include/rexbox/runtime/guest_lock.h`, `src/rexbox/runtime/guest_lock.cpp`)을 더했다.
   * C에서 부를 수 있다. 스레드마다 재귀하고, 바로 못 잡으면 정지 보고용 대기로 표시한다.
   * 2초 시한이 지나면 한 번 보고하고 배제 없이 들어간다.
   * 보고에 스레드 이름을 쓰려고 `thread_activity`에 `CurrentThreadName()`을 더했다.
3. `src/game/jsrf/decomp/adxm_lock.c`: `sub_0013B0A0`(lock), `sub_0013B0E0`(unlock)이 `_gen` 원본을 게스트 잠금으로 감싼다. 다시 생성해 두 함수가 dispatch 표에서 수동 정의를 가리키는 것을 확인했다.

## 검증

| 검증 | 결과 |
|---|---|
| 재생성 | `sub_0013B0A0_gen`, `sub_0013B0E0_gen` 생성. dispatch의 `0x0013B0A0`/`0x0013B0E0`이 새 정의 |
| Release, Debug 빌드 | 새 경고 없음(생성 코드의 기존 D9025만) |
| `rejsrf_decomp_check` / `rejsrf_d3d8_check` / `rexbox_kernel_probe` | 6 case 0 difference / 14018 case 0 difference / 56 check 0 failure |
| 데모 110초(오디오 켬, hidden) | `[stall]`·`[guest lock]` 보고 없음. 1,200 프레임마다 20.0 s, 20.4 s, 20.0 s, 20.0 s(60 fps 유지) |
| 데모 80초, `REXBOX_GUEST_LOCK_TIMEOUT_MS=1` | 보고 없음. 1 ms 넘게 기다린 경합이 없음 |
| 임시 계측(커밋하지 않음) | 70초에 진입 1,000번 이상. thread 2와 thread 4가 들어옴. 두 스레드가 같은 잠금을 쓰는 것을 확인 |
| 사용자 플레이(멈췄던 장면) | 미검증. 사용자 확인 필요 |

* 디컴파일 비교: 이 파일은 원본 본문을 그대로 부르는 어댑터이다. 원본 본문이 HLE(`GetThreadPriority`, `ResumeThread`)를 부르므로 `rejsrf_decomp_check` 사례는 더하지 않았다. 게스트 상태에 주는 영향은 `_gen` 본문과 같다.

## 추가: 대기하는 동안 잠금 내려놓기 (설계 §2.2.1)

* 사용자 확인: 원래 멈춤은 해결됐다. 이후 플레이에서 2초 시한 보고가 나오고 게임이 멈춘 듯했다.
* `guest_lock.cpp`: 스레드마다 가진 잠금 목록을 둔다. `PutDownGuestLocksForWait`/`PickUpGuestLocksAfterWait`를 `NoteWaitBegin`/`NoteWaitEnd`에서 부른다. 시한 보고에 가진 스레드 이름을 넣었다.
* 검증: Release 경고 없음. `rexbox_kernel_probe` 56/0. 데모 110초(오디오 켬)는 60 fps이고 보고가 없다. 데모 70초를 `REXBOX_GUEST_LOCK_TIMEOUT_MS=1`로 돌려도 시한 보고가 없다. 실제 플레이 확인은 사용자에게 필요하다.

## 남은 것

* safe 스레드(`0x0013B180`)는 계속 돈다(설계 §2.3).
* 실제 플레이에서 시한 보고가 나오면, 원본에 있던 "잠금 안 대기"가 있다는 뜻이다. 이 issue에 남긴다.

# Work log: mutual exclusion for the CRI ADXM lock (issue #68)

Design: [20261016-i068](../design/20261016-i068-adxm-lock.md) · Work order: [20261016-i068](../work-orders/20261016-i068-adxm-lock.md)

## Done

1. Matched the user's stall report (v0.0.29) against the disassembly.
   * The presenting thread was in `0x001437B0`'s `GetThreadPriority == 15` loop.
   * The lock it expects is the CRI SVM/ADXM lock. It works on one global count and one saved priority, and its exclusion relies only on single-core priorities ([cri-middleware](../analysis/cri-middleware.md)).
2. Added guest locks to the runtime (`include/rexbox/runtime/guest_lock.h`, `src/rexbox/runtime/guest_lock.cpp`).
   * They are callable from C and recursive per thread, and a wait that cannot take the lock at once is noted for the stall report.
   * After a 2 s limit the waiter reports once and enters without exclusion.
   * `thread_activity` gained `CurrentThreadName()` for that report.
3. `src/game/jsrf/decomp/adxm_lock.c`: `sub_0013B0A0` (lock) and `sub_0013B0E0` (unlock) wrap the `_gen` originals in a guest lock. After regeneration the dispatch table points both at the manual definitions.

## Verification

| Check | Result |
|---|---|
| Regeneration | `sub_0013B0A0_gen` and `sub_0013B0E0_gen` generated; dispatch entries `0x0013B0A0`/`0x0013B0E0` are the new definitions |
| Release and Debug builds | no new warnings (only the generated code's existing D9025) |
| `rejsrf_decomp_check` / `rejsrf_d3d8_check` / `rexbox_kernel_probe` | 6 cases, 0 differences / 14018 cases, 0 differences / 56 checks, 0 failures |
| Demo, 110 s (audio on, hidden) | no `[stall]` or `[guest lock]` reports; 20.0 s, 20.4 s, 20.0 s, 20.0 s per 1,200 frames (60 fps kept) |
| Demo, 80 s, `REXBOX_GUEST_LOCK_TIMEOUT_MS=1` | no reports: no contention longer than 1 ms |
| Temporary trace (not committed) | over 1,000 entries in 70 s, by thread 2 and thread 4: both threads take the same lock |
| User play (the scene that hung) | not verified yet; needs the user |

* Decompilation comparison: the file is an adapter that calls the original bodies as they are. Those bodies call the HLE (`GetThreadPriority`, `ResumeThread`), so no `rejsrf_decomp_check` case was added. The effect on guest state is that of the `_gen` bodies.

## Added: putting the lock down during waits (design §2.2.1)

* The user's check: the original hang is fixed. Later play printed the 2 s timeout report and the game seemed to stop.
* `guest_lock.cpp` keeps per thread the locks it owns; `PutDownGuestLocksForWait`/`PickUpGuestLocksAfterWait` are called from `NoteWaitBegin`/`NoteWaitEnd`. The timeout report names the holder.
* Verification: no Release warnings; `rexbox_kernel_probe` 56/0; a 110 s demo run (audio on) at 60 fps with no reports; a 70 s demo run with `REXBOX_GUEST_LOCK_TIMEOUT_MS=1` without timeout reports. Real play still needs the user.

## Left

* The safe thread (`0x0013B180`) keeps spinning (design §2.3).
* A timeout report in real play would mean the original does wait inside the lock somewhere; record it in this issue.
