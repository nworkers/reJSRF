# Issue #73 작업 로그 — MMATRIX 행렬 스택 함수 디컴파일

작업 지시: [20261016-i073](../work-orders/20261016-i073-mmatrix.md) · 설계: [20261016-i073](../design/20261016-i073-mmatrix.md)

## 요약

게임의 행렬 스택 라이브러리(`MMATRIX` 섹션) 함수 21개를 SSE intrinsic C로 다시 써서 lift 본문을 대신하게 했다. 비교 도구는 이제 XMM 레지스터까지 비교하며 129개 사례가 모두 같다. 같은 데모 구간에서 이 함수들의 샘플이 약 81% 줄었고(프레임당 약 2 ms), 부하가 적을 때의 present 스레드 CPU는 12.3~13.6 ms에서 11.3 ms가 됐다.

## 과정

1. **측정**(v0.0.30, Release, 프레임 2,700~3,300, 샘플 10,607개, 기계 부하 77%):

   | 묶음 | 비율 |
   |---|---|
   | 대기(`ZwDelayExecution`) | 26.3% |
   | lift된 게임 코드 | 25.6% |
   | D3D8 HLE | 14.1% |
   | GL 드라이버(`ig9icd32`, `igc32`) | 약 9% |
   | 그 밖의 ntdll(`ZwSetEvent` 8.1%, `ZwGetWriteWatch` 1.5%, QPC 약 2%) | 약 13% |

   * lift 코드 안에서 `MMATRIX` 섹션의 함수 22개가 744개(lift 코드의 약 28%)였다.
2. **분석**: 섹션을 capstone으로 디스어셈블했다(1,309개 명령, 함수 약 45개).
   * 현재 행렬은 `[[0x264C04]]`다. push/pop, 단위 행렬, 이동, 크기, 곱, 점 변환, sin/cos 표 회전이 있다.
   * 인자는 `ecx`/`edx`이고, 일부는 cdecl 스택 인자다.
   * 섹션 안의 호출은 `1BAC50`(Z·Y·X 회전) → 회전 함수 셋, `1BB0xx` → `1BAE90`뿐이다.
3. **구현**:
   * `src/game/jsrf/decomp/mmatrix.c`: 함수 21개. 같은 lane 연산을 같은 순서와 묶음으로 쓰고, 원본이 메모리를 다시 읽는 곳은 다시 읽는다.
   * 범용 레지스터, esp 아래에 남는 값, XMM0~7을 원본과 같게 남긴다.
   * recomp ABI에 `rexbox_recomp_get_xmm`/`set_xmm`을 더했다.
   * `rejsrf_decomp_check`를 묶음(suite) 구조로 바꾸고 XMM 비교와 함수별 사례 123개를 더했다(6 → 129).
4. **검사의 검사**: 이동의 덧셈 묶음을 일부러 ((x·R0) + (y·R1 + z·R2)) + R3로 바꾸자 6개 사례 중 3개에서 메모리 차이가 났다. 나머지 3개는 반올림 결과가 우연히 같았다. 되돌린 뒤 0개다.
5. **재생성**: 디컴파일 파일이 늘어 `regenerate.py`를 다시 돌렸다(약 11분).
6. **성능**:
   * 비교 기준은 디컴파일 함수가 lift 본문(`_gen`)을 그대로 부르는 임시 빌드다. 커밋하지 않았고, 재생성 없이 만들 수 있다.
   * 기준과 새 빌드를 기준·새·새·기준·기준·새 순서로 실행했다(창 9~12의 CPU 열 평균, ms/프레임).

     | 순서 | 빌드 | CPU |
     |---|---|---|
     | 1 | 기준 | 13.60 |
     | 2 | 새 | 11.33 |
     | 3 | 새 | 11.25 |
     | 4 | 기준 | 12.31 |
     | 5 | 기준 | 20.12 |
     | 6 | 새 | 20.59 |

     * 5·6번은 다른 부하가 들어와 둘 다 크게 올랐고 차이는 흔들림 안이다.
   * 새 빌드를 다시 샘플링했다(샘플 11,098개). 디컴파일 함수(`rejsrf_game`)는 142개, `sub_001BAC50` 25개, `sub_001BAB20` 24개 등이다. 744개에서 약 81% 줄었다.
   * 처음 다시 샘플링했을 때는 기준 빌드를 만들며 링커 map이 덮어써져 이름이 틀리게 붙었다. 다시 빌드해 map과 실행 파일을 맞췄다.

# Issue #73 work log: decompile the MMATRIX matrix-stack functions

Work order: [20261016-i073](../work-orders/20261016-i073-mmatrix.md) · Design: [20261016-i073](../design/20261016-i073-mmatrix.md)

## Summary

21 functions of the title's matrix-stack library (the `MMATRIX` section) were rewritten in C with SSE intrinsics and replace their lifted bodies. The checker now compares XMM registers too, and all 129 cases match. Over the same demo window these functions draw about 81% fewer samples (about 2 ms per frame), and presenting-thread CPU under light load went from 12.3–13.6 ms to 11.3 ms.

## Steps

1. **Measurement** (v0.0.30, Release, frames 2,700–3,300, 10,607 samples, machine load 77%):

   | Group | Share |
   |---|---|
   | waiting (`ZwDelayExecution`) | 26.3% |
   | lifted title code | 25.6% |
   | D3D8 HLE | 14.1% |
   | GL driver (`ig9icd32`, `igc32`) | about 9% |
   | other ntdll (`ZwSetEvent` 8.1%, `ZwGetWriteWatch` 1.5%, QPC about 2%) | about 13% |

   * Within the lifted code, 22 functions of the `MMATRIX` section drew 744 samples (about 28% of the lifted code).
2. **Analysis**: the section was disassembled with capstone (1,309 instructions, about 45 functions).
   * The current matrix is `[[0x264C04]]`. The library has push/pop, identity, translate, scale, multiply, point transforms and sin/cos-table rotations.
   * Arguments come in `ecx`/`edx`, some as cdecl stack arguments.
   * The only calls inside the section are `1BAC50` (Z, Y, X rotation) to the three rotations, and `1BB0xx` to `1BAE90`.
3. **Implementation**:
   * `src/game/jsrf/decomp/mmatrix.c`: 21 functions. Each does the same lane operations in the same order and grouping, and reads memory again where the original does.
   * They leave the general registers, the values below esp and XMM0–7 as the originals do.
   * The recomp ABI gained `rexbox_recomp_get_xmm`/`set_xmm`.
   * `rejsrf_decomp_check` became a set of suites with XMM comparison and 123 more cases (6 → 129).
4. **Checking the check**: changing translate's grouping on purpose to ((x·R0) + (y·R1 + z·R2)) + R3 gave memory differences in 3 of its 6 cases; in the other 3 the rounding happened to agree. Reverted, 0.
5. **Regeneration**: the new decompiled file needs `regenerate.py` (about 11 minutes).
6. **Performance**:
   * The baseline was a temporary build whose decompiled functions just call the lifted bodies (`_gen`). It was not committed, and it needs no regeneration.
   * Baseline and new builds ran in the order base, new, new, base, base, new (the mean CPU column over windows 9–12, ms per frame); the table above has the values.
     * Runs 5 and 6 met other load, both rose sharply, and their difference is within the noise.
   * Sampling the new build again (11,098 samples): the decompiled functions (`rejsrf_game`) drew 142, `sub_001BAC50` 25, `sub_001BAB20` 24 and so on, about 81% fewer than 744.
   * The first resample named functions wrongly: building the baseline had overwritten the linker map. A rebuild brought the map and the executable back in step.
