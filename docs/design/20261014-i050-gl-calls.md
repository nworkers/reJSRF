# 설계: 그리기마다의 GL 호출 줄이기 (issue #50)

선행: [i040 그리기 경로 비용](20261013-i040-draw-performance.md), [i046 HLE 비용](20261014-i046-hle-performance.md), [frame-time §6](../analysis/frame-time.md)

## 1. 요구사항과 측정

* GL 드라이버는 present 스레드 CPU 작업의 약 16%(Intel HD Graphics 620)다. 개발 PC에서는 약 6%다. 저사양 드라이버일수록 호출 하나가 비싸다.
* 어떤 GL 함수를 몇 번 부르는지 센 뒤 많은 것부터 줄인다. 화면은 바뀌지 않아야 한다.
* **측정 도구**: `REXBOX_GL_CALLS=1`(진단).
  * GL 함수 표의 모든 항목이 호출을 세는 래퍼를 거친다. 로더의 각 `Load` 줄이 자기 래퍼 인스턴스를 만들고 드라이버 포인터를 따로 저장한다.
  * `REXBOX_D3D8_PROFILE`가 보고할 때마다 프레임당 호출 수와 상위 16개 함수를 한 줄로 낸다.
* **기준**(Intel HD 620, 2,701~3,000프레임, 그리기 483개): 프레임당 10,505번, 그리기당 약 22번이다.

| 함수 | 프레임당 |
|---|---|
| `glDisableVertexAttribArray` | 3,694 |
| `glVertexAttribPointer` | 1,534 |
| `glEnableVertexAttribArray` | 1,534 |
| `glBindBuffer` | 911 |
| `glUniform4fv` | 861 |
| `glBindFramebuffer` | 487 |
| `glDrawElements` | 480 |
| `glActiveTexture` / `glBindTexture` | 각 290 |

* **확인됨**(코드):
  * 정점 속성 설정이 그리기마다 쓰지 않는 속성(프로그램은 16개 중 나머지, 고정 기능은 7개 중 나머지)을 모두 끄고, 쓰는 속성을 모두 다시 켰다.
  * `BindRenderTarget`은 "다른 경로가 바꾸므로" 그리기마다 프레임버퍼를 다시 묶었다.
  * `glUniform4fv`는 모두 정점 상수 `c[]`였다(임시 계측: 프레임당 831번, 레지스터 3,482개). 바뀐 구간마다 따로 보내 프로그램 그리기당 약 4번이었다.

## 2. 설계

### 2.1 정점 속성 상태 (`d3d8_gl_buffers`)

* 그리기용 VAO가 가진 상태를 기억한다.
  * 켜진 속성의 비트
  * 속성마다 버퍼, 크기, 형식, 정규화, stride, offset
* `SetAttribute(index, …)`: 꺼져 있으면 켜고, 포인터가 기억과 다를 때만 `glVertexAttribPointer`를 부른다.
* `FinishAttributes()`: 이번 그리기에서 이름이 불리지 않은 켜진 속성만 끈다.
* 속성 상태는 VAO의 것이라 다른 코드가 자기 VAO를 묶어도 그대로다. 다만 다음 경우에는 기억을 버린다.
  * VAO를 새로 만들 때
  * 버퍼를 지울 때(포인터 기억만). 지운 버퍼의 이름이 새 버퍼로 돌아와도, VAO는 여전히 옛 버퍼를 가리킬 수 있기 때문이다.

### 2.2 프레임버퍼 바인딩 (`d3d8_gl_targets`)

* `BindRenderTarget`가 마지막으로 묶은 프레임버퍼를 GL 상태 epoch와 함께 기억하고, 같으면 묶지 않는다.
* 프레임버퍼를 바꾸는 다른 경로는 모두 `InvalidateGlStateCache()`를 부른다.
  * present: 원래 부르고 있었다.
  * 화면 덤프: 새로 넣었다.
  * 프레임버퍼 생성: 새로 넣었다.

### 2.3 정점 상수 묶어 보내기 (`UniformCache::SetArray4`)

* 연속된 location의 run마다, 처음 바뀐 원소부터 마지막 바뀐 원소까지를 한 번에 보낸다. 그 사이의 바뀌지 않은 원소도 함께 간다. 호출 하나가 몇십 바이트보다 비싸기 때문이다.
* run은 처음 볼 때 원소마다 "자기 run의 시작"으로 계산해 둔다. 컴파일러가 없앤 원소(location −1)나 끊긴 location에서 run이 나뉜다.

### 2.4 하지 않은 것

* **정점 상수 uniform buffer**: 2.3 뒤 `glUniform4fv`는 프레임당 160번이다. UBO로 바꾸어도 상수가 바뀔 때마다 업로드와 바인딩이 필요해 호출이 더 줄지 않는다.
* **범위마다 VAO**: 남은 큰 몫은 `glVertexAttribPointer`(1,446)와 `glBindBuffer`(912)다. 캐시한 범위마다 버퍼가 달라 그리기마다 다시 가리킨다. (버퍼, 속성 배치)마다 VAO를 두면 그리기당 약 3번이 1번이 된다. 그러려면 다음을 처리해야 한다.
  * 요소 버퍼 바인딩이 VAO 상태라는 점
  * 인덱스 업로드가 VAO를 건드리지 않게 하는 것
  * 버퍼를 지울 때 VAO도 정리하는 것
  
  다음 후보로 남긴다.

## 3. 검증

| 검증 | 기대 |
|---|---|
| `REXBOX_GL_CALLS` | 그리기 483개 구간의 호출 수가 줄어듦 |
| 데모 프레임 2,800~3,400 | 기준 덤프와 같음 |
| present 스레드 CPU(기준과 번갈아 3회) | 줄어듦 |
| Debug/Release, 회귀 도구 | 경고 0, 회귀 없음 |

# Design: fewer GL calls per draw (issue #50)

Prerequisites: [i040 draw-path cost](20261013-i040-draw-performance.md), [i046 HLE cost](20261014-i046-hle-performance.md), [frame-time §6](../analysis/frame-time.md)

## 1. Requirements and measurement

* The GL driver is about 16% of the presenting thread's CPU work on an Intel HD Graphics 620, about 6% on the development PC; a call costs more on low-end drivers.
* Count which GL functions are called how often, then cut the most frequent, with the picture unchanged.
* **Tool**: `REXBOX_GL_CALLS=1` (diagnostic).
  * Every entry of the GL function table goes through a counting wrapper. Each `Load` line of the loader instantiates its own wrapper, which keeps its own driver pointer.
  * Each `REXBOX_D3D8_PROFILE` report adds a line with the calls per frame and the top 16 functions.
* **Baseline** (Intel HD 620, frames 2,701–3,000, 483 draws): 10,505 calls per frame, about 22 per draw. The table in the Korean section applies.
* **Confirmed** (code):
  * Attribute setup disabled every unused attribute on every draw (the rest of 16 for programs, of 7 for fixed function), and enabled every used one again.
  * `BindRenderTarget` bound the framebuffer on every draw, "because other paths change it".
  * Every `glUniform4fv` was the vertex constants `c[]` (temporary counter: 831 calls and 3,482 registers per frame), one call per changed run, about four per program draw.

## 2. Design

### 2.1 Vertex attribute state (`d3d8_gl_buffers`)

* The draw VAO's state is remembered:
  * the enable bits
  * per attribute: buffer, size, type, normalization, stride and offset
* `SetAttribute(index, …)` enables an attribute only if it is off, and calls `glVertexAttribPointer` only when the pointer differs.
* `FinishAttributes()` disables only the enabled attributes this draw did not name.
* This is VAO state, so it survives other code binding its own arrays. It is forgotten in two cases:
  * when the VAO is created
  * when a buffer is deleted (the pointers only), because the name may come back for a new buffer while the VAO still refers to the old one

### 2.2 Framebuffer binding (`d3d8_gl_targets`)

* `BindRenderTarget` remembers the framebuffer it bound, with the GL state epoch, and skips an equal one.
* Every other path that binds framebuffers calls `InvalidateGlStateCache()`:
  * present already did
  * frame dumps now do
  * framebuffer creation now does

### 2.3 Vertex constants in one call (`UniformCache::SetArray4`)

* Per run of consecutive locations, the span from the first changed element to the last goes in one call, unchanged elements in between included, since a call costs more than a few dozen bytes.
* Runs are computed once per program as "the start of my run" per element. They break at elements the compiler dropped (location −1) or at non-consecutive locations.

### 2.4 Not done

* **A uniform buffer for the constants**: after 2.3, `glUniform4fv` is 160 calls per frame. A UBO still needs an upload and a binding per change, so it would not cut calls further.
* **A VAO per range**: the largest remaining shares are `glVertexAttribPointer` (1,446) and `glBindBuffer` (912), since each cached range is its own buffer and every draw re-points. A VAO per (buffer, attribute layout) would turn about three calls per draw into one. It has to handle:
  * the element-buffer binding being VAO state
  * keeping index uploads from touching the VAO
  * deleting VAOs along with buffers
  
  It is left as the next candidate.

## 3. Verification

The table above applies: fewer calls in the 483-draw window under `REXBOX_GL_CALLS`; demo frames 2,800–3,400 equal to a reference dump; lower presenting-thread CPU in three alternating runs against the baseline; Debug and Release with zero warnings and no regressions in the tools.
