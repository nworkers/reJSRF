# 설계: MMATRIX 행렬 스택 함수 디컴파일 (issue #73)

## 1. 문제

* 데모 구간(프레임 2,700~3,300)에서 present 스레드를 샘플링했다(Release, 샘플 10,607개, **확인됨**).
  * 대기(`ZwDelayExecution`)가 26%다.
  * 나머지는 lift된 게임 코드 26%, D3D8 HLE 14%, GL 드라이버 약 9%, 그 밖의 ntdll(`ZwSetEvent` 8% 등)이다.
* lift된 게임 코드 샘플의 약 28%(744개)가 `MMATRIX` 섹션(`0x1BA8A0`~`0x1BBAB0`, 4.6 KB)의 함수 22개에 있다. 대기를 뺀 CPU의 약 9.5%다.
* 이 섹션은 행렬 스택 라이브러리다(**확인됨**, 디스어셈블).
  * `[0x264C04]`는 "현재 행렬 주소를 담은 칸"의 주소다.
  * 행렬은 64바이트 행 우선 4×4 float이고, 행 벡터 규약이다(p' = x·R0 + y·R1 + z·R2 + R3).
  * 회전은 `[0x264BA4]`의 (a, b) float 쌍 표를 16비트 각도로 찾는다(`(angle >> 1) & 0x7FF8`, 산술 시프트). 생김새가 Sega Ninja 라이브러리의 회전 함수와 같다(**추정**).
* 함수마다 SSE 명령 몇 개뿐인데 매우 자주 불린다. lift 코드에서는 호출마다 드는 고정 비용(TLS 레지스터 칸, XMM의 lane별 C 흉내, 스택 정렬 prologue)이 계산보다 크다.

## 2. 설계

* **대상**: 샘플이 12개 이상인 함수 15개와, 함께 쓰이는 단순한 함수 6개, 모두 21개다(`src/game/jsrf/decomp/mmatrix.c`).

| 주소 | 하는 일 | 샘플 |
|---|---|---|
| `1BAB20` | 점 변환(`edx`가 0이면 R3.xyz 복사) | 169 |
| `1BAAA0` | 이동(벡터 포인터) | 100 |
| `1BA9C0` | push(복사) | 84 |
| `1BABA0` | 점 배열 변환 | 67 |
| `1BB330` | Y 회전 | 64 |
| `1BB2E0` | X 회전 | 42 |
| `1BAAE0` | 역이동 | 31 |
| `1BB380` | Z 회전 | 30 |
| `1BADB0` | M = A × M | 24 |
| `1BAC00` | 방향 벡터 변환 | 21 |
| `1BA950` | [ecx] = M | 20 |
| `1BA8F0` | M = [ecx] | 19 |
| `1BAC70` | 표와 작업 벡터로 만든 3×3을 M에 곱함 | 13 |
| `1BAC50` | Z·Y·X 회전 | 13 |
| `1BB270` | 축별 크기 | 12 |
| `1BAA50`, `1BA8A0`, `1BAA00`, `1BA9B0`, `1BAA60`, `1BB2B0` | pop, 단위 행렬, 단위 행렬 push, M 읽기, 이동(스택 인자), 균일 크기 | 0~8 |

* **같은 결과**: 원본과 같은 lane 연산을 같은 순서와 묶음으로 SSE intrinsic으로 계산한다. 예를 들어 이동은 ((x·R0 + R3) + (y·R1 + z·R2))다.
  * IEEE 단정밀도라 lift 코드(lane별 C)와 비트까지 같다.
  * 예외는 NaN 입력의 페이로드다. 컴파일러가 곱셈 피연산자의 순서를 바꿀 수 있다.
* **같은 부수 효과**: 원본이 남기는 것을 그대로 남긴다.
  * 범용 레지스터(`eax`, `ecx`, `edx`의 최종값)
  * 메모리. esp 아래에 남는 push 값과 반환 주소도 포함한다(`1BABA0`, `1BAC50`).
  * XMM0~7. 원본을 부르는 쪽이 XMM 결과를 읽지 않는다고 확인하지 않았으므로 그대로 둔다.
* **읽는 순서**: 원본이 메모리 피연산자로 다시 읽는 곳은 똑같이 다시 읽는다. 별칭(대상과 원본이 겹침)에서도 결과가 같게 하려는 것이다.
  * `1BABA0`은 반복마다 행렬 행을 읽는다.
  * `1BADB0`은 A의 각 행을 이전 결과 행을 쓴 뒤 읽는다.
  * `1BAC70`은 작업 행렬을 쓴 뒤 다시 읽는다.
* **prefetch는 뺀다.** 결과에 영향이 없다.
* **비교 도구(`rejsrf_decomp_check`)**:
  * recomp ABI에 `rexbox_recomp_get_xmm`/`set_xmm`을 더한다.
  * 범용 레지스터·메모리에 더해 XMM0~7도 비교한다.
  * 함수마다 의사난수 행렬·표·인자(씨앗 3개)와 분기 경우를 둔다. 각도 0·음수·상위 비트, `edx` 0, 정렬되지 않은 포인터, 같은 자리 변환, A = M, 배열 개수 1·3·5가 그 경우다.

# Design: decompile the MMATRIX matrix-stack functions (issue #73)

## 1. Problem

* The presenting thread was sampled over demo frames 2,700–3,300 (Release, 10,607 samples, **confirmed**).
  * Waiting (`ZwDelayExecution`) is 26%.
  * The rest is lifted title code 26%, the D3D8 HLE 14%, the GL driver about 9%, and other ntdll (`ZwSetEvent` 8% and more).
* About 28% of the lifted code's samples (744) sit in 22 functions of the `MMATRIX` section (`0x1BA8A0`–`0x1BBAB0`, 4.6 KB), about 9.5% of the non-wait CPU.
* The section is a matrix-stack library (**confirmed**, disassembly).
  * `[0x264C04]` holds the address of the cell that holds the current matrix's address.
  * Matrices are 64-byte row-major 4×4 floats used with row vectors (p' = x·R0 + y·R1 + z·R2 + R3).
  * Rotations look up (a, b) float pairs in the table at `[0x264BA4]` by a 16-bit angle (`(angle >> 1) & 0x7FF8`, arithmetic shift). They look like the Sega Ninja library's rotation functions (**inferred**).
* Each function is a few SSE instructions called very often. Lifted, each call pays more in fixed costs (TLS register slots, the lane-wise C XMM emulation, the stack-aligning prologue) than in arithmetic.

## 2. Design

* **Scope**: the 15 functions with 12 or more samples plus 6 simple companions, 21 in all (`src/game/jsrf/decomp/mmatrix.c`); the table above lists them.
* **Same results**: the same lane operations, in the same order and grouping, through SSE intrinsics. For example, translate is ((x·R0 + R3) + (y·R1 + z·R2)).
  * IEEE single precision makes them bit-identical to the lifted lane-wise C.
  * NaN payloads are the exception, since the compiler may swap a product's operands.
* **Same side effects**: what the originals leave behind is left as is.
  * The general registers (the final `eax`, `ecx`, `edx`)
  * Memory, including the pushes and return addresses left below esp (`1BABA0`, `1BAC50`)
  * XMM0–7, kept because no one checked that callers never read them.
* **Read order**: where the original reads a memory operand again, so do these, so results stay the same under aliasing.
  * `1BABA0` reads the matrix rows in every iteration.
  * `1BADB0` reads each row of A after storing the previous result row.
  * `1BAC70` reads its scratch matrix back after writing it.
* **Prefetches are dropped.** They do not affect results.
* **Checker (`rejsrf_decomp_check`)**:
  * The recomp ABI gains `rexbox_recomp_get_xmm`/`set_xmm`.
  * XMM0–7 are compared as well as the general registers and memory.
  * Each function gets pseudo-random matrices, tables and arguments (three seeds) and its branch cases: angles of zero, negative and with high bits; `edx` zero; unaligned pointers; in-place transforms; A = M; arrays of 1, 3 and 5.
